# 任务集成交付与归档检查方案

本文记录审核后的集成交付与归档流程及其设计背景。该流程已在当前实现中生效；实际运行规则见 [产品需求](./requirements.md) 和 [技术方案](./technical-design.md)。

约束与建议须分别理解：已经确认的约束是审批与交付完成分开、后端检查固定审核提交、所有完成入口统一把关、明确本地目标与检查局限，以及保留事务和授权边界。以下状态组织、字段归属、目录、接口命名、重试次数、UI 排列和实施顺序属于设计建议，不因写入方案就自动成为验收约束。后续任务应按“场景 → 预期结果 → 验证”描述验收，不要求逐步照搬本方案中的实现蓝图。只有开发者确认、既有公共契约要求或架构/安全所需时，才能把这些实现细节升级为约束。实施者可在保持已确认行为、外部契约和架构安全的前提下采用更小、更清楚的实现；新增公共契约需要在实现交付中明确说明。

## 1. 目标与边界

需要进入目标分支的任务，只有满足审核与批准要求，并且后端验证本轮审核提交已经进入目标分支，才能成为 `completed`。归档是完成任务后的展示结果，不是一个绕过业务校验的独立操作。

具体场景：实施代理在 `task/example` 上提交固定 commit `C`，AI 审核通过。即使开发者批准了实现，只要后端无法证实 `C` 已进入目标分支，任务仍须保持可见，提示下一步合并与检查，不进入已完成归档，不解除下游任务的依赖等待。

首版范围：

- 后端对本地 Git 仓库执行只读检查，支持保留审核提交的普通 merge、快进合并，以及直接提交到目标分支的情况。
- 目标是项目约定的本地分支，默认 `main`，也可由开发者明确指定 `develop` 等其他目标；不根据当前检出分支猜测目标，不静默回退到其他分支。具体配置入口属于实施建议。
- 完成表示满足任务验收与本地集成要求，不表示已推送、发布或部署。
- 不执行合并、切换分支、fetch、push，不监听 Git 活动，不增加后台调度或通用 Git 集成框架。
- squash、rebase 后原提交不再可达的情况不自动认定完成；详见第 7 节。

现有 V0 明确排除了广泛的 Git 活动追踪。本方案只为完成门槛引入一次按需检查，不扩展到 diff、命令历史、持续同步或 CI 集成。实施时须同步修订主需求与技术方案中的完成策略。

## 2. 谁负责什么

| 参与方 | 职责 |
| --- | --- |
| 实施代理或开发者 | 提交固定制品；获得明确授权后执行合并及任务要求的验证 |
| 审核代理 | 审核固定提交，记录真实验证证据；不以“审核通过”代替集成证据 |
| 开发者 | 确认目标分支与是否需要 Git 集成，执行必要的最终批准，另行授权合并 |
| WebUI | 展示审核、批准、待集成与检查结果，发起批准或“检查并归档”请求 |
| Git 检查模块 | 在绑定的项目仓库中执行只读命令，返回结构化事实 |
| TaskService | 统一执行批准与完成规则，并原子写入任务、审核记录和事件 |

批准实现、检查 Git 状态和授权合并是不同操作。WebUI 中的“批准”与“检查并归档”均不隐含合并或推送授权。MileStack 不主动启动代理执行合并。

## 3. 审核、批准与完成

必须能够区分审核、最终批准、等待集成和完成，不能把未完成交付的任务当成已完成。建议保留现有六种任务状态，在 `in_review` 中根据最新审核与验收信息派生展示阶段；是否新增顶层状态不作为预先锁定的验收条件，应由实施者结合状态查询和迁移成本判断：

| 阶段 | 条件 | 下一步 |
| --- | --- | --- |
| 等待 AI 审核 | 最新审核为 `pending` 或 `in_progress`，尚未直接验收 | 审核，或由开发者填写原因直接验收 |
| 等待开发者批准 | 中高风险任务最新审核为 `passed`，尚未获最终批准 | 开发者批准 |
| 已验收，等待集成确认 | 已满足风险对应的验收要求，尚未通过完成检查 | 获授权后合并，再点击“检查并归档” |
| 已完成 | 验收要求与交付要求均满足 | `completed`，进入归档 |

按上述状态组织建议，检查错误仍属于待集成确认，不将任务转成执行期的 `blocked`。单纯检查不发放新的实施 `runId`；现有执行和审核凭证的所有权边界必须保持。当前执行人、审核人信息可继续来自原有事件与审核记录。

三个入口统一处理：

| 入口 | 先保存的事实 | 完成规则 |
| --- | --- | --- |
| 已确认低风险的 AI 审核通过 | 审核为 `passed`，记录低风险自动验收 | 立即尝试完成检查；通过才自动完成，否则保留待集成任务 |
| AI 通过后开发者批准 | 记录对最新审核轮次的开发者批准 | 立即尝试完成检查；不通过仍保存批准结果，等待集成 |
| 开发者直接验收 | 审核为 `waived`，记录原因，撤销在途审核凭证 | 立即尝试完成检查；直接验收只替代 AI 结论，不免除 Git 集成要求 |

批准与 Git 检查不能放在一个“检查失败就全部回滚”的事务里。Git 不可用或未合并时，已成功记录的审核、批准或直接验收仍有效，后续无需再次审核或重复批准。

已经验收的任务由开发者点击“检查并归档”重试，不依赖后台轮询自动完成。低风险任务若审核时就已经集成，仍可自动完成。检查通过不替代任务验收要求的集成验证；需要合并后额外验证的任务，必须先按验收条件记录实际证据。

返工或重新打开沿用现有入口。新一轮提交必须重新审核与验收；上一轮批准、检查证据不得使新一轮自动完成。

## 4. 数据设计建议

需要保留以下可追溯的结构化事实，不能靠解析自然语言事件摘要来判断是否允许完成。表格中的记录归属、字段和枚举是建议，不要求照搬到指定表、列或 JSON 嵌套中。

| 位置 | 信息 | 约束 |
| --- | --- | --- |
| Task | 集成要求：`required` 或 `not_required`；目标分支 | 新任务默认 `required`、`main`；只允许开发者侧修改 |
| Task | 无需集成的原因、确认者、确认时间 | `not_required` 必填；AI 不得自行免除检查 |
| TaskReview | 本轮提交时冻结的集成要求与目标分支 | 完成检查绑定该轮次；不能随可移动任务分支变化 |
| TaskReview | 验收来源、验收时间、验收者、直接验收原因 | 来源区分低风险自动验收、开发者批准、开发者直接验收；绑定最新审核轮次 |
| TaskReview | 最终完成证据 | 保存审核 SHA、目标 ref、检测到的目标 SHA、检查时间、检查方式；无需集成时保存开发者确认依据 |

集成要求应由开发者确认，检查结果必须绑定本轮实际交付边界。建议只允许在 `inbox` 或 `ready` 阶段修改，并在提交时冻结；需要变更时经正常退回与重新提交流程处理。允许其他编辑阶段的实现也必须使旧检查证据失效，并记录开发者的变更依据。

纯分析、外部设计等不需要进入仓库的任务，可以由开发者明确设置 `not_required` 并填写原因。这样只免除 Git 包含关系检查，不免除验收或风险审批要求。首版沿用现有固定 commit 审核契约，不在本任务中扩展无 commit 的通用制品审核；完全没有 Git 制品的任务提交流程需另行设计。

无需集成时完成证据应明确记录 `not_required`，不能伪造“已合并”。文档、配置等只要交付物需要进入仓库，也属于 `required`。

## 5. 后端检查算法

检查对象来自最新 `TaskReview` 的固定提交和冻结的目标分支，仓库位置来自当前绑定的项目上下文。提交时携带的 branch/worktree 仅用于展示与定位，不作为执行命令的工作目录或完成依据。

下面的编号流程与命令只说明一种可行实现，不要求逐步照搬。不可削弱的结果是：检查绑定最新审核的固定提交、开发者确认的本地目标和正确项目；Git 检查在数据库事务之外只读执行；无法证明包含关系或检查结果已过期时不完成任务，并说明原因与下一步；完成状态、证据和事件一致写入。实现者可以选择满足这些结果的内部流程与数据组织。

1. 校验当前任务处于允许完成的阶段，最新审核轮次满足风险对应的验收要求。
2. 如本轮明确无需集成，校验开发者确认依据后进入完成事务。
3. 校验绑定目录属于预期 Git 仓库，并检查 Git 可用、审核提交存在、目标是有效的本地分支名。
4. 将 `refs/heads/<targetBranch>` 解析为固定的目标提交 `T`，验证审核提交 `C` 是真实 commit。
5. 执行祖先检查，检查的是两个固定提交，而非执行途中可能变化的分支名。
6. 若检查期间目标 ref 发生变化，不得保存基于旧目标的检查结果；应基于稳定的当前快照重新检查，或返回明确可重试的结果。不规定重试次数。
7. 开启短数据库事务，重新校验任务状态、最新 review ID、审核 SHA、集成要求和验收记录与检查快照一致。
8. 校验通过后，将最终证据、任务 `completed`/`completedAt` 和完成事件在同一个事务中保存；不一致时不完成，要求基于最新轮次重试。

核心命令示意：

```bash
git -C <projectRoot> rev-parse --verify refs/heads/main^{commit}
git -C <projectRoot> cat-file -e <reviewCommitSha>^{commit}
git -C <projectRoot> merge-base --is-ancestor <reviewCommitSha> <targetCommitSha>
```

实现使用 `execFile` 或同类参数数组调用，关闭 shell，验证分支名，设置命令超时及输出上限。不得把任务字段拼成 shell 命令，不执行审核证据里记录的命令文本。

| 检测结果 | 领域结果 | UI 含义 |
| --- | --- | --- |
| 祖先检查返回 `0` | `integrated` | 目标提交包含审核提交，允许完成 |
| 返回 `1`，且仓库历史完整 | `not_integrated` | 未检测到目标分支包含审核提交；保持待集成 |
| 找不到 Git、仓库、目标分支或审核提交；命令超时或异常 | `unavailable` | 无法确认，显示具体原因，不允许完成 |
| 历史不完整且无法证明包含关系 | `unavailable` | 提示缺少历史，不据此断言未合并 |
| 数据库写入时审核轮次等已变更 | `stale_review` | 旧结果失效，刷新最新任务后重试 |

`integrated` 是检查时刻的本地分支快照事实。Git ref 与 SQLite 无法组成一个原子事务，方案不声称能够阻止检查完成之后外部执行 force reset。完成证据保留当时的 `T` 和检查时间，不因后来的分支变动改写历史。

## 6. 架构边界与接口建议

业务规则继续集中于 `TaskService`：

```text
HTTP / MCP -> TaskService -> repository -> SQLite
                  |
                  v
          IntegrationChecker 接口
                  ^
                  |
          本地 Git 只读实现
```

- `src/core` 定义检查输入输出、领域错误、验收和完成规则；不导入具体 Git 进程实现。
- Git 检查实现位于业务核心之外，由项目上下文装配并注入服务，HTTP/MCP 使用同一个实现。可以组织为 `src/git`，具体目录与接口名由实施者选择。
- 缺失检查器时，要求集成的任务不得默认通过。
- Git 进程调用全部发生在数据库事务之外；任务、审核证据、事件写入保持事务一致性。
- 复用规范的 Zod 输入输出，不维护 HTTP/MCP 两套完成规则。

接口调整建议：

- 以下接口路径和响应字段尚未成为既有公共契约，用于说明需要具备的能力，具体命名可调整。
- 现有 `approve` 和 `waive-approval` 返回当前任务与完成检查结果，能够区分“批准已保存，但尚未完成”和“已完成”。检查失败不能显示为批准被撤销。
- 提供开发者侧的重新检查与归档能力，例如 `POST /api/tasks/:id/check-and-complete`；请求绑定预期最新审核，只允许已验收任务重新检查与归档，不顺便授予批准。
- 低风险 MCP 审核通过仍返回任务结果，并明确携带当前交付阶段与下一步；不能通过其他适配器绕过完成门槛。
- 查询只读取持久数据并派生阶段，不在项目状态轮询、任务列表或详情 GET 中运行 Git。页面上次检查结果只供展示，归档必须重新检查，不能信任缓存。
- 本轮通过之后始终保留 `passed` 或 `waived` 事实，直接验收会继续撤销原 `reviewRunId`。

## 7. squash、rebase 与检查失败

首版判断的是提交可达性，不比较补丁是否相同：

- 原审核提交已在目标分支历史中，即使任务分支已删除，也可以通过。
- squash 或 rebase 可能使原审核 SHA 不在目标历史中。检查返回未包含时，提示“未检测到审核提交进入目标分支；若使用了 squash/rebase，本检查无法证明集成”，不声称代码一定未交付。
- 首版不接受仅填写一个新 SHA 就替代审核 SHA，也不提供通用“忽略 Git 错误并归档”按钮。采用这些合并方式前，应明确该限制。
- 如后续支持提交映射，必须另外设计原审核制品与实际集成提交之间的验证和审计，不能覆盖原审核 SHA。
- 缺失目标分支、Git 不可用或仓库位置错误时，提示修复对象与原因，不切换到 `origin/main`，不 fetch，不选择当前分支作为替代。

## 8. WebUI 交互

页面必须能区分“待 AI 审核”“待开发者批准”“已验收，待集成确认”。建议继续放在现有待审核区域，避免额外看板；区域划分随最终状态设计确定。

以下为非约束性的布局示意，元素顺序、按钮名称和排列尚未由开发者逐项确认。验收关注状态、目标、审核提交、检查原因和下一步是否清楚可见，不要求复刻排版：

```text
任务标题 / ID
AI 审核通过 · 已获开发者批准 · 待集成确认
目标：本地 main    审核提交：abc123…
未检测到审核提交进入 main。请在获授权后合并并完成必要验证，再重试。
[检查并归档] [查看审核记录] [退回返工]
```

- 未经最终批准的中高风险任务展示“批准”；已验收但尚未完成的任务展示“检查并归档”。
- 批准或直接验收成功但检查未通过时，显示“批准已保存，任务待集成”，不显示归档成功。
- 检查过程中禁用重复请求并显示“正在检查”；失败后保留任务和具体原因，允许重试。
- 检查通过才显示“已完成并归档”，刷新任务列表、完成数量、归档和依赖状态。
- 详情展示固定审核 SHA、源分支、目标分支、验收来源及最终完成证据；目标明确标注“本地”。
- 无需集成的任务显示“无需 Git 集成”和开发者填写的原因，不显示“已合并”。
- 更新低风险自动完成提示，只有真实满足验收与交付要求才显示自动完成，不再仅凭低风险和 `completed` 推断完成来源。

## 9. 迁移与实施顺序

使用前向迁移增加所需字段；升级已有非空数据库前创建并验证备份。不改已发布迁移，不删除数据库。

建议的历史处理方式如下；必须保持已有完成记录与真实证据，不得伪造检查结果。非完成任务的默认配置和恢复方式应结合现有数据确定：

- 既有 `completed` 保持完成，不自动重新打开，不伪造合并或批准证据；缺少新证据时展示为历史记录未核验。
- 尚未完成的历史任务默认要求本地 `main` 集成；已提交的最新 review 固定该默认值，界面明确展示。目标不正确时使用正常退回与重新提交流程修正。
- 历史 `in_review` 的最新 `passed` 低风险审核，或 `waived` 审核，可根据真实审核/事件事实恢复相应验收信息；无法无歧义恢复时保留待开发者处理，不推测批准。
- 已有运行中的审核凭证、执行凭证和风险确认不因字段迁移被无故废除。

按一个完整交付 outcome 实施。一种可选顺序是先数据与核心完成规则，再 Git 检查与项目装配，再 HTTP/MCP 和 WebUI，最后同步主需求、技术设计、用户指南和生成的代理指令；实施者无需逐步照搬该顺序。实现与验收记录保存在对应 MileStack 任务，本文件不维护动态进度。

## 10. 验收与验证

核心验收场景：

1. 分支提交通过 AI 审核但未进入目标分支时，低风险自动完成、人工批准和直接验收三个入口均不归档；审核和批准事实仍保存。
2. 普通 merge、快进合并、直接在目标分支提交、合并后删除任务分支均能正确完成；不要求源分支仍存在。
3. “检查并归档”只能用于已验收的最新轮次；中高风险未批准、过期 review ID、新提交或返工均不能利用旧批准完成。
4. Git 检查异常、目标不存在、提交缺失、历史不足、超时或检查器未装配均不误完成；可读提示与重试正确。
5. 检查期间审核轮次、任务状态、验收依据或目标快照变更时，不将旧证据用于新任务状态；并发归档只产生一次完成事件。
6. 任务、最终证据与完成事件原子写入；失败回滚不留部分完成记录，待集成任务不解除下游依赖。
7. squash/rebase 不被误判为已验证；页面准确表达检查局限。
8. 开发者显式确认无需集成的任务按原风险要求完成；AI 不能设置该豁免，直接验收也不能默默免除集成检查。
9. 带既有任务与审核记录的数据库可安全迁移，历史归档保持，既有证据与有效凭证保留。
10. WebUI 能清楚区分批准成功、等待集成、无法检查与归档成功；HTTP/MCP 与页面遵循相同业务规则。
